# 📐 项目架构设计知识卡 — 可复用原则

> **用途**：以后做新项目时，在规划阶段直接引用本卡，确保架构从第一天就满足
> 分工明确、可扩展、易管理、节约 Token、方便长期运维的标准。
> 来源：Agent Hub 项目架构设计过程中沉淀。

---

## 一、架构健康检查 7 维度

> 每个新项目启动时，用以下 7 个维度快速评估现状或设计合理性。

### 1. 项目结构与模块边界
- [ ] 目录结构一看就懂（5分钟内理解分层）
- [ ] 每个文件只做一件事（单一职责）
- [ ] 新增功能只需改 ≤ 2 个文件
- [ ] 无循环依赖、无隐式耦合
- [ ] 配置不散落在代码中，集中管理

### 2. 路由与流程控制
- [ ] 路由逻辑不用 if/elif 堆叠（注册表驱动）
- [ ] 新增路由 = 新建文件 + 注册一条，零改动现有代码
- [ ] 路由策略分层：精确匹配 → 模式匹配 → AI兜底

### 3. 执行引擎
- [ ] 有统一的 executor（context in → result out）
- [ ] 每个任务模块（skill）接口一致（标准签名）
- [ ] 任务崩溃不传播到其他任务

### 4. 横切关注点（Hook/中间件）
- [ ] 日志、鉴权、计时、审计用中间件统一处理
- [ ] Hook 可叠加、可禁用、可按优先级排序
- [ ] 业务代码内无散落的 log/auth/timing 调用

### 5. 外部依赖抽象
- [ ] 每个外部依赖有抽象接口（AI模型、消息渠道、数据源）
- [ ] 切换实现 = 改配置，不改代码
- [ ] 删除一个实现文件不影响其他模块

### 6. 配置与安全
- [ ] 敏感信息（Token/Secret）从环境变量注入
- [ ] 配置文件结构清晰（YAML/JSON），非开发者可修改
- [ ] 配置变量有默认值、有验证

### 7. 可运维性
- [ ] 一键启动所有服务
- [ ] 单个模块故障不拖垮总体
- [ ] 执行历史自动记录（零人工审计日志）
- [ ] 有清晰的版本号和变更追踪

## 二、5 层架构模式（通用模板）

```
L0 — 接入层（Channel）     协议适配 → 统一 Context
L1 — 核心层（Core）         路由 + 执行引擎 + 中间件管道 + 注册表
L2 — 业务层（Bot/Module）   每个业务模块独立目录（skills + prompts + memory）
L3 — 工具层（Tools）        无状态原子操作，所有模块共享
L3 — 能力层（Providers）    外部能力抽象（AI模型、外部API等）
```

### 设计原则

| 原则 | 说明 | 检验方法 |
|------|------|---------|
| **向下依赖** | 上层可调用下层，下层不感知上层 | Channel 不 import Skill，Skill 不 import Channel |
| **接口隔离** | 每层通过抽象接口交互 | 替换任一实现文件，其他层不受影响 |
| **数据统一** | 全链路一个 Context 对象 | 每一层只读写自己的字段 |
| **自动发现** | 新增模块不需注册代码 | 放入目录即自动加载 |
| **配置驱动** | 行为由配置文件决定，非硬编码 | 改 YAML 即可调整行为 |

## 三、关键设计模式速查

### 3.1 注册表自动发现模式

```
问题：新增功能需要在多处注册、修改路由表
方案：扫描目录下所有 .py 文件，提取 MANIFEST 变量自动注册
效果：新增功能 = 新建文件（含 MANIFEST + handle 函数），零改动现有代码
适用：skill/tool/hook/channel/provider 等所有可扩展模块
```

### 3.2 Channel 抽象模式

```
问题：需要接入多种消息渠道（飞书/微信/HTTP/CLI）
方案：定义 ChannelBase 接口（start + send_reply），每个渠道独立文件实现
效果：切换渠道 = 改配置文件一行
适用：任何需要多入口的系统
```

### 3.3 Provider 抽象模式

```
问题：需要使用多种 AI 模型，可能随时切换
方案：定义 ProviderBase 接口（call + check_available + call_with_retry）
      优先级：模块指定 > 业务域默认 > 全局兜底
效果：切换AI = 改配置，skill 代码完全不变
适用：任何调用外部 AI/API 的系统
```

### 3.4 业务隔离模式（多Bot/多模块）

```
问题：多个业务域（投研/健康/日报）需要共存但互不干扰
方案：每个业务域一个目录，拥有独立的 skills/prompts/memory/config
      各自实例化独立的 registry/pipeline/pending_store
      共享全局 tools 和 providers
效果：新增业务域 = 复制模板 + 填配置 + 写技能，零改动框架
适用：任何多业务域共存的平台
```

### 3.5 Token 三级优化模式

```
第一级 路由层：能用关键词匹配就不调 AI（覆盖 60%+ 场景）
第二级 Prompt层：按需裁剪 context，只注入必要的信息
第三级 对话层：长对话前半段压缩为摘要，减少历史注入
```

### 3.6 可拔插验证法

```
验证方法：删除模块 X → 重启 → 其他模块正常运行
通过条件：
  - 删 skill → 该指令返回"未注册"，其他正常
  - 删 hook → 无该功能但不崩溃
  - 删 channel → 仅影响使用该渠道的Bot
  - 删 provider → 仅影响使用该模型的Bot/Skill
  - 删 tool → 仅影响调用该工具的 skill
  - 删 Bot → 其他Bot正常
  - 删 core/ → 系统崩溃（预期，框架骨架不可删）
```

## 四、施工流程标准化

### 4.1 项目规划阶段

```
1. 画分层架构图（确定有几层、每层放什么）
2. 定义核心数据结构（统一 Context 对象）
3. 定义 4 个抽象接口（Channel/Provider/Skill/Hook 的签名）
4. 写 bot.yaml / registry.yaml 配置格式
5. 输出验收对照单（每个施工项有验收命令）
```

### 4.2 施工阶段

```
Phase 1 — 地基：Core层 + Channel + Provider + 最简Tool + Hook + 模板
         验收门禁：模板Bot可ping通

Phase 2 — 迁移：按复杂度递增逐个迁移业务功能
         每迁一个立即测试，不批量迁移
         验收门禁：全部功能正常工作

Phase 3 — 扩展：新增业务域 + 清理旧代码
         验收门禁：多Bot共存 + 可拔插验证
```

### 4.3 验收阶段

```
逐条对照验收单打勾
阶段门禁全部通过才进入下阶段
最终验收 7 项全过 = 项目交付
```

## 五、反模式清单（踩过的坑）

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 上帝文件（单文件>500行） | 改一处影响全局 | 按职责拆分为独立文件 |
| 路由用 if/elif 堆叠 | 新路由改3+个文件 | 注册表驱动 |
| API Token 硬编码 | 泄密风险 | 环境变量注入 |
| 路径硬编码 | 环境迁移必崩 | 配置文件 + 相对路径 |
| 全局变量共享状态 | 多模块污染 | 每个模块独立实例 |
| tool 持有状态 | 跨模块副作用 | tool 纯函数，状态放调用方 |
| 横切逻辑散落在业务代码 | 改认证逻辑改50个文件 | 中间件管道统一处理 |
| 全量注入 context 给 AI | Token 浪费 | 按需裁剪 |
| 一次性批量迁移 | 回归测试爆炸 | 逐个迁移+即时测试 |
| 配置和代码混在一起 | 非开发者无法修改 | YAML 配置外部化 |
