# 📐 架构设计与运维知识卡 — 可复用原则

> **用途**：以后做新项目时引用本卡，确保架构从第一天就满足分工明确、可扩展、节约 Token 的标准。  
> 来源：Agent Hub 项目三轮迭代沉淀（设计 → 施工 → 加固 → 维护）。

---

## 一、架构健康检查 7 维度

> 每个新项目启动时用以下 7 个维度快速评估。

| 维度 | 检查项 |
|------|--------|
| 1 模块边界 | 目录结构5分钟理解；新功能改≤2文件；无循环依赖 |
| 2 路由控制 | 注册表驱动不堆 if/elif；新路由=新文件 |
| 3 执行引擎 | 统一 executor；任务崩溃不传播 |
| 4 横切关注 | 日志/鉴权/计时用中间件；Hook可叠加可禁用 |
| 5 依赖抽象 | 每个外部依赖有接口；切换=改配置 |
| 6 配置安全 | 敏感信息环境变量注入；YAML配置外部化 |
| 7 可运维性 | 一键启动；单模块故障不拖垮总体；审计日志自动记录 |

---

## 二、5 层架构模式（通用模板）

```
L0 — 接入层（Channel）     协议适配 → 统一 Context
L1 — 核心层（Core）         路由 + 执行引擎 + 中间件管道 + 注册表
L2 — 业务层（Bot/Module）   独立目录（skills + prompts + memory）
L3 — 工具层（Tools）        无状态原子操作，所有模块共享
L3 — 能力层（Providers）    外部能力抽象（AI模型、API等）
```

| 原则 | 检验方法 |
|------|---------|
| 向下依赖 | Channel 不 import Skill，Skill 不 import Channel |
| 接口隔离 | 替换任一实现文件，其他层不受影响 |
| 数据统一 | 全链路一个 Context 对象，每层只读写自己的字段 |
| 自动发现 | 放入目录即自动加载 |
| 配置驱动 | 改 YAML 即可调整行为 |

## 三、关键设计模式速查

| 模式 | 问题 | 方案 | 效果 |
|------|------|------|------|
| 注册表自动发现 | 新功能需多处注册 | 扫描目录提取 MANIFEST | 新功能=新文件，零改旧代码 |
| Channel 抽象 | 多消息渠道 | ChannelBase 接口 | 切换渠道=改配置一行 |
| Provider 抽象 | 多AI模型 | ProviderBase + 三级优先链 | 切换AI=改配置 |
| 业务隔离 | 多Bot共存 | 独立目录+独立注册表+独立进程 | 新业务=复制模板 |
| Token 三级优化 | Token 浪费 | 路由层关键词>Prompt层按需裁剪>对话层历史压缩 | 覆盖60%+场景零Token |
| 可拔插验证 | 模块耦合 | 删模块→重启→其他正常 | 只有删 core/ 才崩 |

## 四、架构加固铁律（实战沉淀）

### 铁律1：共享代码只存一份，差异通过覆盖实现
```
_shared/skills/  ← 共享，只维护一份
bot_a/skills/    ← 空（用共享的）
bot_b/skills/x.py ← 放同名文件覆盖
```

### 铁律2：新增功能 = 新增文件，不改旧代码
新功能做成独立 tool/skill 文件。即使新文件崩溃，旧功能降级不受影响。

### 铁律3：每个数据字段"单一写入者"
```
Channel 写 → request_id, user_id, raw_text
Router 写  → matched_skill, parsed_args
Executor 写 → workspace, ai_provider, metadata
Skill 写   → reply_text, status, output_path
```
在 Context docstring 里写明归属表。

### 铁律4：路由层不做业务判断，业务层不做路由判断
能单步完成的流程不做两步。两步增加路由复杂度和出错可能。

### 铁律5：入口文档是"代码的一部分"
```
CLAUDE.md 改动频率 ≥ 代码改动频率
```

### 铁律6：反直觉设计在两处说明（代码注释 + 文档）
任何人看了会问"这是 bug 还是设计"的代码，必须写清楚"为什么"。

### 铁律7：Token 控制在代码层实现，不在 Prompt 层限制
```python
# ✅ 代码层截断
kb_context = search_kb(query, ws, max_files=3, max_chars_per_file=1500)
# ❌ Prompt 层限制（AI 经常忽略）
"请简洁回答，限300字"
```

### 铁律8：Shared 代码访问 Bot 级资源，必须通过 runtime 注入
```python
# ❌ 硬编码相对路径（__file__ 指向 _shared/，找不到 bot 目录下的文件）
prompt_file = Path(__file__).parent.parent / 'prompts' / 'system' / 'classify.md'
# ✅ 从 runtime 动态获取 bot 的实际目录
prompt_file = runtime.bot_dir / 'prompts' / 'system' / 'classify.md'
```
教训来源：`_classify_intent` 路径永远找不到 → 分类全部退化 → 研报被当公司交流处理。

### 铁律9：AI 输出进入文件系统前，必须经过净化函数
```python
# ❌ 信任 AI 输出直接当路径
full_path = Path(ws) / ai_output_path
full_path.parent.mkdir(parents=True)  # 创建任意目录！

# ✅ 清理后再用
clean_path = sanitize_path(ai_output_path)  # 去反引号/非法前缀/强制后缀
full_path = Path(ws) / clean_path
```
AI 是"不可信输入源"，等同于用户输入。`mkdir(parents=True)` + 未净化路径 = 任意目录创建。

### 铁律10：Prompt 必须区分执行上下文
同一 Prompt 被两种管道复用时（如 CLI 直接调用 vs `--print` 管道调用），对文件系统操作的指令必须隔离：
- CLI 模式：AI 有文件系统权限，可以写指令让它操作文件
- 管道模式：AI 无文件系统权限，只负责输出内容，由代码层处理 IO

违反后果：AI 混淆上下文 → 输出含 `_Inbox/` 等物理路径 → 代码层盲目创建目录。

## 五、防幻觉三层策略

| 层级 | 方法 | 效果 |
|------|------|------|
| Prompt 层 | "不知道就说不知道" 铁律 | ~70% |
| 数据层 | 只给 AI 已验证的 context（知识库/联网 snippet）| 最有效 |
| 输出层 | 联网信息标注「📡 来源于联网搜索」 | 用户可判断 |

## 六、文档设计原则

### 6.1 分层文档

| 层级 | 文件 | 读者 | 核心内容 |
|------|------|------|---------|
| 入口层 | CLAUDE.md | agent 首次读取 | 目录结构、约束、路由速查 |
| 架构层 | docs/00_架构总览.md | 理解系统 | 数据流、分层、已知问题 |
| 模块层 | 各目录 README | 修改模块 | 职责、接口 |
| 代码层 | 函数注释 | 修改函数 | 为什么、边缘案例 |

### 6.2 文档有效性自检

> **A**：新 agent 只读 CLAUDE.md，能找到功能对应的文件吗？  
> **B**：agent 修完 bug，知道还需要同步更新哪些文件吗？

### 6.3 文档更新触发器

| 修改类型 | 必须更新 |
|---------|---------|
| 修改 core/*.py | CLAUDE.md + docs/00_架构总览.md |
| 新增/修改 Skill | CLAUDE.md（Skill 流程表）|
| 修改 router.py | CLAUDE.md（路由速查）|
| 新增 tools/ | CLAUDE.md（项目结构）|
| 修改目录结构 | CLAUDE.md + docs/00 |

## 七、施工流程标准化

```
Phase 1 — 地基：Core + Channel + Provider + 模板 → 验收：模板Bot可ping通
Phase 2 — 迁移：按复杂度递增逐个迁移 → 验收：全部功能正常
Phase 3 — 扩展：新增业务域 + 清理旧代码 → 验收：可拔插验证全过
```

## 八、反模式清单

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 上帝文件（>500行）| 改一处影响全局 | 按职责拆分 |
| 路由用 if/elif 堆叠 | 新路由改3+文件 | 注册表驱动 |
| API Token 硬编码 | 泄密 | 环境变量注入 |
| 共享代码 Copy 多份 | 早晚不一致 | _shared 共享+覆盖 |
| 全量注入 context 给 AI | Token 浪费 | 按需裁剪 |
| 文档和代码不同步 | agent 被误导 | 触发器表强制同步 |
| 两步流程能单步完成 | 路由复杂度增加 | 能单步就单步 |
| Shared 代码用 `__file__` 找 Bot 级文件 | 路径永远解析错 | 通过 runtime 注入 bot_dir |
| AI 输出直接当文件路径 | 任意目录创建/路径腐化 | `sanitize_path()` 净化后再用 |
| 同一 Prompt 服务不同权限上下文 | AI 混淆后输出有害指令 | 拆分 Prompt 或注入时过滤 |

## 九、架构健康度自检清单

```
□ CLAUDE.md 目录结构反映当前代码？
□ 有没有新的"文件副本"关系？
□ 新增代码文件是否独立（删掉不影响其他）？
□ Context 字段有没有被意外新增？
□ core/ 文件有没有被修改？理由充分？
□ python3 -c "import ast; ast.parse(...)" 全部通过？
□ Shared Skill 是否通过 runtime 访问 Bot 级资源（而非硬编码路径）？
□ AI 输出进入文件系统前是否经过 sanitize？
□ Prompt 中有无文件系统操作指令在管道模式下不适用？
```
