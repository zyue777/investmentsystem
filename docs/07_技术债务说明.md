## TD-01：Skill 反向 import executor（循环依赖）

### 现象

所有包含 AI 调用的 Skill 都写了这一行：

```python
# bots/investment/skills/kb_query.py
from core.executor import get_ai_provider
```

这形成了一个方向相反的依赖：

```
core/executor.py
    → 通过 Registry 调用 skill.handle(ctx)   ← "正向"（框架调业务）
    
bots/*/skills/*.py
    → from core.executor import get_ai_provider  ← "反向"（业务调框架）
```

### 为什么现在没问题

Python 的模块加载机制允许这种"运行时循环"，因为：
- executor.py 并不在模块顶层 import skill 文件
- skill 文件也不在模块顶层 import executor（它在函数体内 import）
- 两者的循环是"使用时"发生的，不是"加载时"发生的

### 未来什么情况下会出问题

1. **如果 executor.py 需要在模块顶层 import 某个 skill**（不应该，但万一）
2. **如果 core/ 被打包成独立库复用**，Skill 无法直接 import 宿主项目的 executor
3. **如果新开发者不理解**，可能在 Skill 中通过 executor 调用其他 Skill，形成真正的循环调用链

### 影响范围

所有调用 AI 的 Skill（目前 8 个）：
`kb_query`, `ingest_record`, `ingest_url`, `phase_execute`, `dialog_mode`, `framework_update`, `crystallize`（部分），`system_status`（不调用 AI）

### 优化方案（遇到时再做）

**方案：把 `get_ai_provider` 在 executor.py 中直接注入到 ctx 里**

```python
# core/executor.py — Step 3 注入时增加一行
import functools
ctx.metadata['get_provider'] = functools.partial(
    _get_provider_by_name, runtime.provider_registry, runtime.config.ai_provider
)
```

```python
# Skill 内部改为：
provider = ctx.metadata['get_provider'](ctx.ai_provider)
# 不再需要 from core.executor import get_ai_provider
```

这样 Skill 只依赖 `core.context.Context`，不依赖 `core.executor`，循环彻底消除。

**改动成本**：修改 executor.py 一处 + 所有 Skill 中替换一行 import。改动量可控，但非紧急。

## TD-02：dedup Hook 使用进程内全局变量

### 现象

```python
# hooks/dedup.py
_processed_ids: set = set()   # ← 进程内 Python 全局变量
```

### 为什么现在没问题

当前架构下，每个 Bot 独立进程 + 独立飞书应用（不同 APP_ID）：

```
investment Bot（进程A）   ← 连接 clinic_a94b 飞书应用
investment_ds Bot（进程B）← 连接 cli_a94ba 飞书应用（另一个）
```

同一条消息的 `message_id` 只会被一个飞书应用收到，两个进程的 `_processed_ids` 永远不会重叠，所以**各自去重是完全正确的**。

### 未来什么情况下会出问题

**触发条件**：多个进程监听同一个飞书应用（负载均衡、高可用场景）

```
场景：investment Bot 起了两个副本（进程C + 进程D），共用同一个 APP_ID
→ 同一条消息被 C 和 D 同时收到
→ C 的 _processed_ids 里没有，放行处理
→ D 的 _processed_ids 里也没有，也放行处理
→ 同一条消息被处理两次，用户收到重复回复
```

当前项目**不存在这个场景**，每个飞书应用只有一个进程监听，所以是安全的。

### 次要问题：内存重启清零

进程重启后 `_processed_ids` 清空，如果飞书在重启瞬间重发了消息，可能被重复处理。概率极低，飞书重发窗口约 5 秒，而消息处理通常 < 3 秒。

### 优化方案（遇到时再做）

**方案：换用 Redis 或 SQLite 做持久化去重**

```python
# hooks/dedup.py 替换方案
import redis, os

_redis = redis.Redis(host='localhost', port=6379, db=0)
DEDUP_TTL = 3600  # 1小时内去重

def handle(ctx: Context) -> Context:
    key = f"dedup:{ctx.request_id}"
    if _redis.exists(key):
        ctx.status = ContextStatus.CANCELLED
        return ctx
    _redis.setex(key, DEDUP_TTL, 1)
    return ctx
```

**更轻量方案（不引入 Redis）**：用 SQLite 文件做共享去重存储，进程间通过文件锁协调。

**当前建议**：维持现状，除非出现多进程共享飞书应用的需求再改。

## TD-03：kb_query 硬编码知识库目录结构

### 现象

```python
# bots/investment/skills/kb_query.py

def _load_dossier(ws: str, industry: str) -> str:
    cards_dir = Path(ws) / '研究' / '论点卡'     # ← 硬编码
    ...

def _get_tree_summary(ws: str) -> str:
    ...
    for d in sorted(kb.iterdir()):
        count = sum(1 for _ in d.rglob('*.md'))  # ← 只扫 .md，隐含假设
```

类似问题也出现在 `ingest_record.py`：

```python
output_dir = p_cfg.get('output_dir', '')   # 来自 registry.yaml，相对好一点
```

### 为什么现在没问题

投研工作台的目录结构已稳定（`研究/论点卡/`、`知识库/`、`_Inbox/`），短期内不会变。

### 未来什么情况下会出问题

1. **知识库目录重命名**：改了目录名，`_load_dossier` 找不到文件，`析` 指令失效，但不会报错（返回空字符串），AI 会产出质量差的分析——**静默失败，难以发现**
2. **复制 Bot 给第二个知识库用**：新知识库目录结构不同，需要改 Skill 代码而不是改配置
3. **同一 Bot 服务多个知识库**：无法为不同知识库配置不同的目录映射

### 影响范围

`bots/investment/skills/kb_query.py` 的 `_load_dossier()` 和 `_get_tree_summary()`

### 优化方案（遇到时再做）

**方案：把目录结构配置移到 bot.yaml 中**

```yaml
# bot.yaml（增加 knowledge_structure 字段）
workspace: "/home/zy/桌面/投研工作台"
knowledge_structure:
  论点卡: "研究/论点卡"
  行业知识库: "知识库/行业"
  研究底稿: "研究/个股底稿"
  inbox: "_Inbox"
```

```python
# kb_query.py 中读取
runtime = ctx.metadata.get('_runtime')
ks = getattr(runtime.config, 'knowledge_structure', {})
cards_dir = Path(ws) / ks.get('论点卡', '研究/论点卡')   # 配置优先，硬编码兜底
```

**改动成本**：
- `BotConfig` dataclass 增加 `knowledge_structure: dict` 字段（1行）
- `bot.yaml` 增加配置块（5行）
- `kb_query.py` 修改两个函数（10行）
- 向后兼容：配置缺失时 fallback 到原硬编码路径

**当前建议**：当目录结构发生第一次变更时，顺便做这个优化。

## TD-04：Channel 层硬编码文件消息路由

### 背景

2026-04-13 新增文件录入功能（`ingest_file` Skill）时，为了让飞书文件消息绕过 Router（触发词匹配）直接进入处理链，在 `channels/feishu_ws.py` 中写了这段代码：

```python
# channels/feishu_ws.py — on_message 分支
elif msg.message_type in ('file', 'doc'):
    ...
    ctx.matched_skill = 'ingest_file'   # ← 硬编码 Skill 名
    ctx.status = ContextStatus.ROUTED
    threading.Thread(target=self._handle_direct, ...).start()
```

同时在 `core/executor.py` 中补了一个"预路由跳过"逻辑：

```python
# core/executor.py
if ctx.status != ContextStatus.ROUTED:
    ctx = runtime.router.route(ctx)
```

### 现在为什么没问题

目前项目里所有文件类型（`.docx` / `.pdf` / `.txt` / `.md`）走的都是同一个 Skill（`ingest_file`），硬编码映射是正确的，没有歧义。

### 未来什么情况下会出问题

**触发条件**：需要对不同文件类型路由到不同 Skill 时

```
场景：以后想加图片识别功能
→ 你发一张图片（message_type = 'image'）
→ Channel 代码里没有 image 分支 → 被 else 跳过，无响应
→ 需要再改 feishu_ws.py 加一个 elif 分支
→ 每加一种文件类型，就要改一次 Channel 代码

场景：以后想让 Excel → 数据录入 Skill，PDF → 文件蒸馏 Skill，Word → 情报卡 Skill
→ 每种映射都要在 Channel 里硬编码一行
→ Channel 变成了一个"隐形路由表"，职责越界
```

**根本矛盾**：文件消息缺少"文字触发词"，Router 的触发词匹配机制天然不适用于它，但 Channel 层又不应该承担业务路由决策。

### 影响范围

- `channels/feishu_ws.py`：现有的 `file/doc` 分支
- `core/executor.py`：`status != ROUTED` 跳过逻辑（本身设计合理，可保留）
- 未来新增 `image` / `audio` / `video` 等消息类型时，每次都需要改 Channel

### 优化方案（遇到时再做）

**方案：在 bot.yaml 中配置文件类型→Skill 映射，Channel 读配置动态路由**

```yaml
# bot.yaml（增加 file_skill_routes 字段）
file_skill_routes:
  file: ingest_file       # .docx / .pdf 等
  doc:  ingest_file       # 飞书文档
  image: ingest_image     # 未来：图片分析 Skill
  audio: ingest_audio     # 未来：语音转写 Skill
```

```python
# channels/feishu_ws.py — 不再硬编码，改为读配置
elif msg.message_type in runtime.config.file_skill_routes:
    skill_name = runtime.config.file_skill_routes[msg.message_type]
    ctx.matched_skill = skill_name
    ctx.status = ContextStatus.ROUTED
    threading.Thread(target=self._handle_direct, args=(ctx,), daemon=True).start()
```

```python
# core/bot_runtime.py — BotConfig 增加字段
@dataclass
class BotConfig:
    ...
    file_skill_routes: dict = field(default_factory=lambda: {'file': 'ingest_file', 'doc': 'ingest_file'})
```

**改动成本**：
- `BotConfig` 增加一个字段，有默认值（向后兼容，不改 bot.yaml 也能跑）
- `feishu_ws.py` 把硬编码的 `elif` 替换为读配置（5行）
- 新增任何文件类型支持：只改 bot.yaml，零代码改动

**当前建议**：下次新增文件类型（image/audio）时顺便做这个改造。现在改收益不大。
