## 二、发现的问题及处理建议

### 🔴 问题1：executor.py 被 Skill 反向 import（循环依赖风险）

**位置**：所有包含 AI 调用的 Skill

```python
# bots/investment/skills/kb_query.py
from core.executor import get_ai_provider   # ← Skill 反向 import Core
```

**现状**：虽然 Python 可以处理这个循环（因为 executor.py import 的是 skill 的 handler 函数，不是模块），但这是一个隐性依赖，会让人误以为 Skill 可以独立运行。

**建议**（非紧急）：
```python
# 方案：在 context.py 中定义 get_provider 协议，让 Skill 从 ctx 自身取
# ctx.get_provider() → 无需 import executor
# 当前架构稳定可用，作为未来重构点记录
```

**风险等级**：低（当前无实际 bug，只是代码组织不优雅）

---

### 🔴 问题2：dedup hook 使用进程内全局变量

**位置**：`hooks/dedup.py`

```python
_processed_ids: set = set()   # ← 进程内全局变量
```

**分析**：
- `investment` Bot（主进程）和 `investment_ds` Bot（子进程）各有独立进程
- 两个 Bot 使用不同的飞书应用（APP_ID 不同），同一条消息的 `message_id` 不会被两个 Bot 同时收到
- **结论：当前架构下这不是 bug，是安全的**

**若未来需要同一飞书应用多进程处理消息**，则需改为 Redis 或文件锁实现持久化去重。

### 🟡 问题3：kb_query 中硬编码了知识库目录结构

**位置**：`bots/investment/skills/kb_query.py`

```python
def _load_dossier(ws: str, industry: str) -> str:
    cards_dir = Path(ws) / '研究' / '论点卡'   # ← 硬编码目录名
```

**影响**：如果知识库目录结构变更，需要手动修改代码。

**建议**：将目录结构配置放到 `bot.yaml` 中：

```yaml
# bot.yaml（未来可添加）
knowledge_dirs:
  论点卡: "研究/论点卡"
  行业知识库: "知识库/行业"
```

**风险等级**：低（当前目录结构稳定）

### 🟡 问题4：ingest_record 内部直接访问 `runtime._phase_configs`

**位置**：`bots/investment/skills/ingest_record.py`

```python
runtime = ctx.metadata.get('_runtime')
phase_configs = runtime._phase_configs   # ← 访问私有属性
```

**分析**：`_phase_configs` 带下划线前缀，是"私有"属性。Skill 直接读取 runtime 内部属性，违反了"Skill 只通过 ctx 和 tools 访问资源"的原则。

**建议**：在 executor.py 中将 `phase_configs` 也注入到 `ctx.metadata`：

```python
# executor.py 中增加一行
ctx.metadata['_phase_configs'] = runtime._phase_configs
```

这样 Skill 就可以通过 `ctx.metadata.get('_phase_configs')` 读取，不再需要访问 runtime 私有属性。

**风险等级**：低（当前无 bug）

---

### 🟡 问题5：daily_report Bot 游离在 BotLoader 之外

**位置**：`bots/daily_report/`

**现状**：
- `bot.yaml` 中 `enabled: false`，BotLoader 跳过
- `scheduler_runner.py` 直接调用 `daily_reporter/` 的函数，不经过 Router/Middleware/Hook 管道

**影响**：
- audit Hook **不生效**（scheduler_runner 有自己的 `_audit()` 函数替代）
- dedup/auth Hook **不生效**（定时任务不需要，无影响）
- 如果有 Bug，无法从 `executions.jsonl` 里追溯

**当前缓解措施**：scheduler_runner.py 内置了 `_audit()` 函数，写入自己的 `executions.jsonl`，可追溯。

**建议**（未来）：开发 `scheduler` Channel 类型，让 APScheduler 驱动的 Bot 也能通过标准管道运行。
