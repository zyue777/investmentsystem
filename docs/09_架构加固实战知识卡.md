# 架构加固实战知识卡 — 可复用原则

> 版本：2026-04-13 | 来源：investment_system Agent Hub 项目三轮加固实战
> 适用场景：任何多 Bot / 多模块 AI 应用项目的长期维护

---

## 一、核心目标

**"小修小补不牵全身"** — 任何单一 Bug 修复只需改 1-2 个文件，不引发级联改动。

---

## 二、架构加固七条铁律

### 铁律1：共享代码只存一份，差异通过覆盖实现

**问题**：多个模块使用完全相同的代码，但各自维护独立副本。改一处必须同步改所有副本。

**解法**：

```
正确做法（覆盖模式）：
  _shared/skills/         ← 共享代码，只维护一份
  bot_a/skills/           ← 空目录（用共享的）
  bot_b/skills/my_skill.py ← 有特殊需求时放同名文件覆盖

错误做法（Copy 模式）：
  bot_a/skills/kb_query.py  ← 内容相同
  bot_b/skills/kb_query.py  ← 手动同步（早晚忘记）
```

**加载顺序**：共享先加载 → 模块专属后加载（同名 key 覆盖）。利用注册表的 dict 特性天然支持。

---

### 铁律2：新增功能 = 新增文件，不改旧代码

**问题**：给系统加联网搜索能力。

**错误做法**：直接改 `kb_query.py`，在里面 import requests + 写搜索逻辑。混合关注点，一旦搜索出 bug 影响知识库问答。

**正确做法**：
```
新建 tools/web_search.py   ← 独立工具，不依赖任何 Skill
新建 tools/kb_search.py    ← 独立工具，不依赖任何 Skill
修改 skills/kb_query.py    ← 调用新工具（import + 3 行调用代码）
```

即使两个新 tool 完全崩溃，`kb_query.py` 最多降级到原来的行为（catch 住异常，fallback 到目录摘要），不影响录入/蒸馏等其他流程。

---

### 铁律3：状态流转设计"单一写入者"

每个数据字段只由一个层写入：

```
Channel 写 → request_id, user_id, raw_text
Router 写  → matched_skill, parsed_args
Executor 写 → workspace, ai_provider, metadata
Skill 写   → reply_text, status, output_path
```

**必须在 Context dataclass 的 docstring 里写明归属表。**
Agent 看到归属表，就不会在 Skill 里去改 `request_id`（那是 Channel 的事）。

---

### 铁律4：路由层不做业务判断，业务层不做路由判断

**反例（发生过的 bug）**：
- `ingest_file` 用两步确认流程（预览 → ok → 写入），但 Router 不认识 `ok` 应该路由回 `ingest_file`
- 结果 `ok` 进了 AI fallback，DeepSeek 自己编了一条"✅ 已入库"让用户误以为成功

**修复后的原则**：
- 需要确认的流程，由 `pending_store` 管理状态，Router 第0层优先路由
- 不需要确认的流程（如 `ingest_file`），直接入库，一步到位
- **能用单步流程的，不用两步**——两步增加了路由复杂度

---

### 铁律5：入口文档是"代码的一部分"

```
CLAUDE.md 改动频率 ≥ 代码改动频率
```

每次代码重构后，第一个 PR 应该是更新 CLAUDE.md。检查三项：
1. 目录结构是否准确
2. 有没有新增的"文件依赖关系"要声明
3. 有没有新的"反直觉设计"要说明

---

### 铁律6：反直觉设计必须在两个位置说明（代码 + 文档）

**反直觉设计定义**：任何开发者（或 agent）看了会问"这是 bug 还是设计"的代码。

**例子**：
```python
# ⚠️ triggers 为空是设计，不是 bug。
# 文件消息由 Channel 层直接注入 matched_skill='ingest_file'，绕过 Router。
# 详见 CLAUDE.md「特殊路由」章节和 docs/07_技术债务说明.md TD-04。
MANIFEST = SkillManifest(
    name="ingest_file",
    triggers=[],   # 无文字触发词
)
```

---

### 铁律7：Token 控制在代码层实现，不在 Prompt 层限制

**错误做法**：在 prompt 里写"请简洁回答，限300字"（AI 经常忽略）

**正确做法**：
```python
# 代码层控制输入 context 的大小
kb_context = search_kb(query, ws, max_files=3, max_chars_per_file=1500)  # 上限 4500 字
web_context = search_web(query, max_results=5)  # 上限 1000 字 snippet

# 代码层截断 AI 输出
reply = raw[:REPLY_MAX_LEN] + "\n\n…（内容过长）" if len(raw) > REPLY_MAX_LEN else raw
```

## 三、防幻觉三层策略

| 层级 | 方法 | 效果 |
|------|------|------|
| Prompt 层 | 反幻觉铁律指令（"不知道就说不知道"） | 约 70% 有效 |
| 数据层 | 只给 AI 已验证的上下文（知识库文件/联网 snippet） | 最有效 |
| 输出层 | 联网信息标注「📡 来源于联网搜索」，区分知识库数据和实时数据 | 用户可自行判断 |

## 四、联网搜索集成模式

```
用户指令（明确触发，零 Token 成本判断）
    ↓
  「请联网回答 xxx」         → use_web=True, use_kb=False
  「请结合联网与知识库xxx」  → use_web=True, use_kb=True
  「问 xxx」                → use_web=False, use_kb=True
    ↓
数据收集（零 Token）
  ├── 知识库搜索（本地 grep + 读文件）
  └── 联网搜索（DuckDuckGo API）
    ↓
AI 调用（一次 Token 消耗）
  prompt = 反幻觉指令 + 知识库上下文 + 联网摘要 + 用户问题
    ↓
输出（带来源标注）
```

**关键**：搜索决策在代码层（用明确的触发词前缀），不消耗 Token。AI 只在最后一步被调用一次。

## 五、技术选型备忘

| 需求 | 选择 | 理由 |
|------|------|------|
| 联网搜索 | DuckDuckGo（`ddgs`包） | 免费，无需 API Key，结构化结果 |
| 知识库搜索 | 本地 grep + 文件读取 | 零成本，足够准确 |
| Skills 共享 | 同名覆盖模式 | 利用 Registry dict 特性，零框架改动 |
| 防幻觉 | Prompt 铁律 + 数据控制 + 输出标注 | 三层叠加，比单层可靠 |
| Google Search API | ❌ 已关闭新用户注册，2027年下线 | 不可选 |

## 六、架构健康度自检清单

每次做完大的改动后，跑一遍这个清单：

```
□ CLAUDE.md 目录结构是否反映当前代码？
□ 有没有出现新的"文件必须同步"关系？
□ 新增的代码文件是否是独立的（删掉不影响其他功能）？
□ Context 字段有没有被意外新增（检查 context.py）？
□ core/ 目录的文件有没有被修改？如果有，理由是否充分？
□ 能否用 python3 -c "import ast; ast.parse(...)" 跑通所有文件？
```
